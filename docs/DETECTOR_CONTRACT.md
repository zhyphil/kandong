# 检测与裁剪移植前的规则核验

2026-09-24，等待目标华为缩放对照安装确认期间的独立准备；仅运行固定宿主依赖的预处理/排序函数，没有加载检测模型或改变既有识别结果。Android检测和裁剪仍待实现。

## 发现与证据

使用RapidOCR3.9.2实际安装源码，指纹和10个尺寸边界在[核验记录](evidence/detector-contract/2026-09-24/audit.json)。[固定版本检测入口](https://github.com/RapidAI/RapidOCR/blob/v3.9.2/python/rapidocr/ch_ppocr_det/main.py)与本地行为一致：

- 原实验配置`limit_side_len=1280, limit_type=max`，但`get_preprocess`根据输入最长边选择960（小于960）、1500（小于1500）、2000（其余）。旧文档“最大边1280”已修正；没有改原始报告的配置字段或模型输出。
- 先按比例取整，再以32为单位做Python偶数舍入。100×1499输入得到96×1504，不能把被选的1500当最终张量硬上限；16像素高可舍入成0并返回空，17×48得到32×64。不能用Kotlin/Java通常的半入整数规则替代。
- 实际检测入口会重新排序框，但返回的scores保留原序。用两个框的假后处理输出复现：框顺序由右/左变为左/右，而分数仍0.2/0.9。记录明确标为假后处理/无神经推理，仅证明数据关联问题；后续移植应把ID、框和分数作为整体排序。原宿主OCR公开报告的文字分数来自识别器，不据此宣称原文字置信度错误。

复现脚本：[check-detector-contract.py](../scripts/check-detector-contract.py)，使用既有固定临时依赖，显式指定仓库外输出目录；不下载模型，不读用户图片。

## 后续实现必须覆盖

1. 冻结检测模型实际输入/输出，记录整图预处理比例、补边和32倍数后的尺寸；在分配前检查最终形状/字节数，不能只检查配置值。
2. 阈值、dilation、框得分、polygon expansion和透视变换均核对该版本实际配置与输出。不能用简单扩大矩形冒充同一算法；候选框截断应保留不完整状态。
3. 框、得分和稳定块ID一起排序；透视裁剪及竖排旋转保留返回原图的坐标关系，再按模型批次顺序恢复原块对应。
4. 数值推理、几何位置、英法中文识别质量分别验收；空白、极窄、边缘和多块条件均保留负例。不对已知答案选模型或补词，不从此核验推断全屏可用。

这份核验不代替当前[Android缩放真机门槛](ANDROID_RESIZE.md)，也没有让正式放大镜开始识别屏幕。
