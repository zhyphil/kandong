# MVP 与实施阶段

## Phase0：技术验证

交付可构建 Kotlin/Compose 工程、中文披露/权限入口、手动会话、只读可见节点快照、确定性候选、基于真实 bounds 的触摸穿透高亮，以及独立测试页和验证说明。

验收：读取/切换不改变测试按钮计数；用户真实触摸才触发一次；窗口/内容变化或15秒过期清除结果；输入/密码/敏感子树不进入快照；停止能清理；构建、单元测试、Lint和跨 App 设备测试提供实际证据。当前状态以 [VALIDATION](VALIDATION.md) 为准。

此阶段排除 AI、云服务、OCR、截图、翻译、语音、自动动作和产品发布。桌面上生成代码不算设备验证；模拟器通过不算全机型通过。

## Phase1：“帮我看看 / 看懂”（计划，未实施）

1. 先选一个合成外语购票场景，和真实长辈确认“当前页面是什么、哪些条款重要、哪里不懂”；避免真实付款数据。
2. 定义 `ScreenExplanation` 契约：summary、importantItems、warnings、evidenceNodeIds、可选 targetNodeId、无法确认的原因。每项解释必须能追溯到当前快照，不能编造费用、行程或点击后果。
3. 先完成本地演示 provider 与契约测试；再选择真实理解/翻译方案。若需云端，另做明确的单次上传同意、脱敏预览、提供商/留存披露、最小网络权限和失败降级，不默认发送屏幕。
4. 将开发候选面板替换为大字“帮我看看”入口：一段短解释、重要条款、用户挑选的“这是什么”。下一步控件只在依据足够且快照仍有效时高亮，仍由人点击。
5. 用真实长辈完成非敏感任务观察；衡量是否理解、能否找到按钮、能否停用，记录误导/无法解释与失败原因。达到明确验收后再考虑 OCR、TTS或放大。

先修复 Phase0 真机适配中发现的问题，再开展上述行为改动。HarmonyOS NEXT 单独研究，不把 Android APK 当作通用方案。
