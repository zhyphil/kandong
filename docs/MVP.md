# MVP 路线与验收

## Phase 0A — Magnifier Technical Spike（当前第一任务）

用户在真实 Android 手机上打开 Chrome、SNCF 或其他第三方 App → 启动看懂 → 出现局部放大镜 → 移动/拉伸取景框 → 通过双指捏合或独立1～5倍滑杆查看原文，超出镜面时在画面内滑动 → 底层布局保持原样。本阶段无需 AI，也不读取页面文字。官方原生路线不采集截图；用户指定的华为兼容路线在每次明确屏幕共享授权后接收屏幕帧，仅复制局部区域显示，不保存或上传。

官方系统窗口路线的能力比较见 [MAGNIFICATION](MAGNIFICATION.md)。目标华为使用独立compat：中文入口、自由调整取景框宽高、独立1～5倍滑杆（默认2倍）及镜面内滑动、放大窗自动避让与停止。官方app模块保留原验证交互；其系统镜框没有通用尺寸setter，不把兼容版能力套用到原生版。

Go 条件：至少一台明确记录型号/Android 版本的实体手机，在合成页 + Chrome 普通网页 + 一个第三方 App 通过开关、默认2倍与1/5端点及至少两个非预设倍率、选区/倍率互不影响、红框直接拖动、右上角自由宽高调整、双指缩放/滑杆双向同步、镜面内滑动到全部选区、上下自动避让、连续拖动/边缘到达、滚动/切页、无 reflow、收起后正常手动操作、停止/锁屏清理。记录实际使用的路线、App及其限制；旧版固定倍率测试不替代新交互验收。API 请求返回 true 和模拟器截图都不能单独满足真机 Go。

No-Go/转备选条件：所选设备没有窗口放大能力；只能得到全屏模式；无法稳定移动/关闭；放大导致不可接受遮挡、操作负担或区域几何无法为翻译提供可靠依据。按具体设备记录结论，再决定是否研究截图自绘方案，不静默降级。

当前实际结果见 [VALIDATION](VALIDATION.md)。没有实体手机证据时只能标记“技术实现/模拟器验证完成，真机 Go/No-Go 待定”。

## Phase 0B — Magnifier Translation（下一开发阶段）

链路：当前前台页面整屏可见信息 → Accessibility Tree优先、缺失时按需本机OCR（首批EN/FR/ZH及同屏混排） → 带位置和语义关系的屏幕上下文 → 选区命中元素及关联上下文 → FR/EN到中文、已有中文保留原文 → 放大窗内对应元素的译文。红框限制显示，不限制理解范围；详见[上下文契约与验收](TRANSLATION_CONTEXT.md)。

1. 首先验证源区域坐标与节点坐标映射，处理窗口偏移、旋转、裁剪、重复节点和动画时效；API34 `getBoundsInWindow` 可避免放大缩放，API33 的屏幕 bounds 不能直接当原坐标使用。旧 WindowSelector 不能原样复用。
2. 用户点“中文”时获取一次整屏可见上下文，保留块ID、原文和标题/条件/卡片的关系。同一有效页面内移动红框重新匹配元素；页面滚动/内容变化立即撤下旧译文。收起/菜单/停止取消在途结果，恢复后重新获取，不延用旧坐标。
3. 本机OCR只作为fallback，识别当前可见页面的上下文，不能先丢弃红框外信息。先验证自有镜面遮挡、树与像素非原子同步、文字块缺失及重复；临时隐藏自有窗的一次采集方案尚待验证。不默认连续截图，不读取屏外或隐藏窗口；安全窗口拒绝时停止。
4. 本机模型除了中文/法语/英语质量、体积、首次下载、离线表现和许可，还必须验证利用页面上下文及逐元素返回对应译文的能力。单字符串翻译通过不代表整屏上下文通过；未选定最终模型，不伪装已实现。联网或云处理另行披露，不静默切换。
5. 分别验证英语、法语、中文与混排识别，中文简体/繁体分列结果；中文源文字不能用预置中文译文代替验收。覆盖小字、数字/单位、重音、标点与否定，不以平均成绩掩盖关键错误。先用合成整屏场景核对红框外标题/单位/否定、重复按钮跨卡片归属、选区切断语句、动态页面和迟到结果。原有12条单句语料继续用于基础质量检查，不能替代上下文测试。再在目标华为验证SNCF、航空公司页面、Chrome外语网页和Settings等真实场景，只留去内容化指标与人工判定，避免记录真实个人资料。
6. 译文优先在镜面对应元素处排布，超长或归属不确定时提供与原文关联的可读卡片/未识别提示，不强行压字或错误覆盖。测量整屏读取、识别、翻译及渲染各段耗时/峰值内存，确认收起后均暂停。

成功标准：看不清 → 打开放大镜 → 看清；看不懂 → 点中文 → 就地看到忠实译文，并能切回原文。先验证这一核心差异，再开发 AI。

## Phase 1 — AI 帮我看懂

用户点“帮我看懂”才根据当前区域/页面，用短句解释含义。区分翻译、事实和推断；突出费用、日期、行李、退款限制；缺证据就说明无法确认。先定义可追溯文本证据契约，再选择模型和传输方案。绝不默认上传整个屏幕。

## Phase 2 — 下一步怎么办

Screen understanding → next action → semantic target → node resolver → 实际 bounds → overlay highlight → human taps。只有此阶段才接回 `experiments/guidance` 中审查后的节点/高亮能力；补齐旧原型未完成的设备稳定性和放大坐标验证。ScreenSaathi 只作这一层的技术参考。禁止自动点击、输入、购买、支付、确认、提交。

## Phase 3 — Elder UX / TTS / Safety / Performance

真实长辈可用性测试、朗读、高对比度、极简手势、敏感内容防护加强、本地优先、延迟/电池/内存测量。基础安全已从 Phase 0A 实施。Android13、不同 OEM、导航方式、折叠屏、TalkBack 共存需逐步扩展矩阵；不并行开做 iOS 或 HarmonyOS NEXT。

## Phase0A日常体验完善

兼容版先完善收起/恢复、可拖动贴边按钮、紧凑图标控制、精简首页和菜单。帮助/隐私本版可用；翻译、账号、订阅只明确预留，不在本阶段接入OCR、联网、登录或支付。恢复保留当前选区/倍率/镜面偏移；收起暂停处理，结束释放共享。设计与设备验收分别见[UX](UX.md)和[VALIDATION](VALIDATION.md)。
